# srath.dk

Website for **SRATH**, a Danish sole proprietorship that develops and publishes mobile applications on Google Play.

- Static HTML/CSS, generated by a small Node.js script. **No dependencies** (`npm install` is not needed).
- Hosted for free on **GitHub Pages**, deployed automatically by GitHub Actions on every push to `main`.
- No cookies, analytics, tracking scripts, or third-party fonts.
- App pages and privacy policies are generated from one data file and one Markdown file per app.
- `app-ads.txt` for Google AdMob is copied to the site root byte for byte, and checked after every build and every deployment.

## Project structure

```
content/
  site.json              Business name, contact email, CVR, about text, LinkedIn
  projects.json          Non-app projects on the home page (e.g. the webshop)
  partners.json          Suppliers and partners (/partners/)
  games.json             Browser games (/games/)
  apps.json              One entry per application
  privacy/
    _TEMPLATE.md         Starting point for a new policy (ignored by the build)
    <app-slug>.md        Privacy policy for each app
public/                  Copied unchanged to the site root
  app-ads.txt            Google AdMob authorised sellers file
  CNAME                  srath.dk
  robots.txt, favicon.*, apple-touch-icon.png, og-image.png
  images/apps/<slug>/    App icons and screenshots
src/
  build.mjs              Static site generator: pages, sitemap and checks
  templates.mjs          Layout and reusable components
  markdown.mjs           Small Markdown renderer for the policies
  styles.css, main.js    Published under /assets/
scripts/
  verify.mjs             Post-build checks: app-ads.txt, required files, broken links
  check-live.mjs         Checks the deployed https://srath.dk/app-ads.txt
  serve.mjs              Local preview server
.github/workflows/deploy.yml
```

## Local development

You need Node.js 18.17 or later (CI uses Node 24).

```bash
npm run dev        # build, serve http://localhost:4321 and rebuild on changes (refresh the browser)
npm run check      # build + verify (the same checks CI runs)
npm run preview    # build once and serve
npm run verify:live   # check the live https://srath.dk/app-ads.txt
```

The build fails with a clear message when content is invalid, for example a missing field, a duplicate slug, a missing image or a missing privacy policy. It prints **warnings** for anything that is not ready to publish: sample apps, placeholder policies, or an empty email address.

## Site configuration

Edit `content/site.json`:

| Field | Purpose |
| --- | --- |
| `email` | **Required before launch.** Contact address used in every mailto link and the `{{contactEmail}}` placeholder in policies. |
| `tagline` | Short line used in the home page title and footer. |
| `about` | The "About" text on the home page. Markdown, so links like `[text](https://example.com)` work. |
| `linkedin` | Your LinkedIn URL, shown on the home page and in the footer. Leave empty to hide. |
| `legal.owner` | Owner of the sole proprietorship, shown under business information on the contact page. |
| `legal.cvr` | Your CVR number, shown in the footer and on the contact page. Danish law generally requires businesses to show their CVR number on their website. |
| `legal.address` | Optional. Shown on the contact page if set. |
| `url` | `https://srath.dk`. Used for canonical URLs and the sitemap. |
| `description` | Used for search engines and social previews. |

## Projects on the home page

The home page lists everything in `content/projects.json` (for example the Baiganyo webshop), followed automatically by every app in `apps.json`.

```json
{
  "name": "Baiganyo",
  "type": "Webshop",
  "status": "Opening soon",
  "description": "An upcoming webshop.",
  "url": "https://baiganyo.dk",
  "linkLabel": "baiganyo.dk",
  "logo": "/images/projects/baiganyo-logo.svg"
}
```

`name`, `type` and `description` are required. Use `icon` for a square icon, or `logo` for a wide logo (shown on a light tile, like Baiganyo's moustache). Without either, the card shows the first letter of the name. When the webshop opens, change `status` (for example to `"Open"`) and write a proper `description`.

## Browser games

`content/games.json` lists the games. Each game's own files live in `public/games/<slug>/` and are copied unchanged. The build creates `/games/` (the list) and `/games/<slug>/` (the game page, inside the normal site layout), adds a Games tab to the menu and puts each game on the home page.

```json
{ "slug": "gridword", "name": "Gridword", "tagline": "One line for cards.", "description": "Longer text under the game.", "icon": "/games/gridword/icon.svg" }
```

A game folder must contain `game.js`, and may contain `game.css` and `words.js` (loaded before `game.js`). The page provides an empty `<div id="<slug>">` for the game to fill. Games must not load anything from other sites or use cookies or ads, so the website privacy notice stays true. Progress may be stored in `localStorage`; the privacy page mentions this automatically while any game exists.

On the home page, all games share a single "Browser games" card that links to `/games/`.

**BREACH://** (`public/games/breach/`) is a terminal puzzle game in one file, `game.js`. It simulates a fictional version of SRATH's own systems (the machine `srath`, hosts `db.srath`, `mail.srath`, `releases.srath`): a filesystem, users, hosts and ports, a small SQL database and processes. The game states clearly that none of it is real. There are six missions, and each one reveals one fragment of the access key.

- **Editing the puzzles:** the story, files and data are plain objects near the top of `game.js` (`LEVELS`, `ACHIEVEMENTS`, `HOSTS`, `FS`, `DB`). The fragments and the admin password are constants at the very top. If you change the Base64 or cipher text, re-encode it: the Vigenère key is the codename in the `projects` table.
- **Real projects:** two places list SRATH's real projects and must be updated when a project is added or changes status: the release server easter egg (`connect releases.srath 21`, in `releases()`) and the `projects` table in `DB`. The project marked `classified` in that table is BREACH itself, and its codename is the cipher key.
- **The vault:** winning links to `/games/breach/vault/`. The build generates that page (`"vault": true` in `games.json`) from the site's real projects, apps and other games. It's hidden from search engines, the sitemap and the menus.
- **Saved progress:** progress, achievements and history are saved in the visitor's browser under `breach:v2`. Players can type `reset confirm` to start over.
- **Testing:** in the browser console, `localStorage.removeItem('breach:v2')` and a reload give a fresh start.

**Trails** (`public/games/trails/`) is an arcade game: dots leave lines, you steer only left and right, and touching a line knocks you out. Gaps open in each line every few seconds (with a warning ring), and during your own gap you can hop over lines. It has computer dots, two players on one keyboard, nine power-ups that can each be switched off in the menu, and full screen.

- **Tuning:** speed, turn rate, line width, gaps and power-up timing are constants at the top of `game.js`. `POWERUPS` lists each power-up with its duration and how often it appears.
- **Fixed simulation:** the game runs on a fixed 1000×680 arena with a fixed 120 Hz timestep. That's deliberate: the planned online mode lets one player's browser run the game and send positions to the others.
- **Saved settings:** stored in localStorage (`trails:setup`, `trails:muted`).
- **Testing:** `__trails.give('boost')` and `__trails.state()` in the browser console help when testing.

**Gridword** (`public/games/gridword/`) is a daily five-letter word game:

- `words.js`: `answers` (hand-picked common words, one per day, shuffled with a fixed seed) and `valid` (all other accepted guesses, from the public-domain ENABLE word list).
- The daily word depends only on the visitor's local date. Gridword #1 is 13 November 2026, and the 793 answers last until January 2029. To add answers, append to the list. Keep the existing order, or past and future days change.
- Statistics and today's progress are saved in the visitor's browser under `gridword:v1`.

`content/partners.json` lists suppliers and partners, for example the webshop's suppliers. They appear on `/partners/`, grouped by `project`, and the first six also appear on the home page.

```json
[
  {
    "name": "Supplier name",
    "type": "Supplier",
    "project": "Baiganyo",
    "description": "What they supply.",
    "url": "https://supplier.example",
    "logo": "/images/partners/supplier.svg"
  }

```

`name` and `type` are required. `url`, `description`, `logo` (wide) or `icon` (square) and `linkLabel` (defaults to the domain) are optional. ## Adding an application

1. Add the icon (and optional screenshots) under `public/images/apps/<slug>/`. Use a 512×512 PNG for the icon (the same as on Play) and portrait screenshots, ideally 1080×2340 or similar, in WebP/PNG/JPG.
2. Add an entry to `content/apps.json`:

   ```json
   {
     "slug": "my-app",
     "name": "My App",
     "tagline": "One sentence shown on cards and as the page description.",
     "description": "Longer description.\n\nSeparate paragraphs with a blank line.",
     "category": "Productivity",
     "packageName": "dk.srath.myapp",
     "icon": "/images/apps/my-app/icon.png",
     "playStoreUrl": "https://play.google.com/store/apps/details?id=dk.srath.myapp",
     "features": ["Optional", "bullet points"],
     "screenshots": [{ "src": "/images/apps/my-app/1.webp", "alt": "Main screen" }],
     "status": "Under development"
   }
   ```

   Required: `slug`, `name`, `tagline`, `description`, `icon`. Optional `status` (for example "Under development") is shown instead of "Coming soon" while there is no Google Play link. The `slug` becomes the permanent URL (`/apps/my-app/`, `/privacy/my-app/`), so **do not change it after you have given the privacy URL to Google Play.** The order in the file is the order shown on the site.
3. Create `content/privacy/<slug>.md` from the template (see below).
4. Run `npm run check`, then commit and push.

**Apps that are not on Google Play yet:** leave `playStoreUrl` empty. The app page then shows a disabled "Coming soon to Google Play" button, and the build prints a reminder. When the app is live, paste its link (`https://play.google.com/store/apps/details?id=<package>`) and push.

**Sample data:** an entry with `"sample": true` gets a "Sample" badge and is hidden from search engines. This is useful for trying out layouts. Do not publish one.

## Privacy policies

Each app's policy lives in `content/privacy/<slug>.md` and is published at `https://srath.dk/privacy/<slug>/`.

```markdown
---
lastUpdated: 2026-11-07
placeholder: false
---

## Introduction

This privacy policy explains how {{appName}} ...
```

- `lastUpdated` (YYYY-MM-DD) is shown at the top of the page. Update it whenever you change the policy.
- `placeholder: true` shows a "Placeholder" warning on the page and hides it from search engines. Set it to `false` once the text is your real, reviewed policy.
- `{{appName}}`, `{{developerName}}`, `{{contactEmail}}`, `{{lastUpdated}}` and `{{websiteUrl}}` are replaced during the build, so changing your email only takes one edit.
- A table of contents is added automatically when the policy has three or more `##` headings.
- Supported Markdown: `##`/`###` headings, paragraphs, `-` and `1.` lists, `**bold**`, `*italic*`, `[links](https://…)`, `<name@example.com>`, `>` quotes, `---` and raw HTML blocks (for example a `<table>`). HTML comments are removed.

### Migrating from Google Sites

1. Create the file: copy `content/privacy/_TEMPLATE.md` to `content/privacy/<slug>.md`.
2. Replace the placeholder sections with your existing policy text. Keep only the sections that apply to that app, such as AdMob, analytics or other third-party SDKs. The template lists the usual topics but does not make any claims.
3. Set `placeholder: false` and the correct `lastUpdated`, then deploy.
4. Open `https://srath.dk/privacy/<slug>/` and check it on your phone.
5. In Play Console, update the app's privacy policy URL (**Policy and programs → App content → Privacy policy**) to the new URL.
6. Keep the Google Sites page online until Play Console has accepted the new URL for every app.

## app-ads.txt

`public/app-ads.txt` contains exactly:

```
google.com, pub-4316823278364195, DIRECT, f08c47fec0942fa0
```

It is followed by a single LF line ending. Several measures keep it intact:

- Everything in `public/` is copied verbatim. The build never parses or rewrites it, and it fails if `dist/app-ads.txt` differs from the source by even one byte.
- `.gitattributes` forces LF line endings, so Git on Windows cannot turn them into CRLF.
- `npm run verify` (run in CI before every deployment) checks for the exact AdMob line, no BOM, no CR characters and no HTML.
- After every deployment, the `verify-live` job fetches `<site>/app-ads.txt` and checks HTTP 200, `Content-Type: text/plain` and exact content. GitHub Pages serves `.txt` files as raw `text/plain`, without redirects or authentication.

To add another ad network later, add its line to `public/app-ads.txt`. Keep the Google line unchanged.

## First-time deployment

The order of these steps follows GitHub's guidance: verify the domain and add it to the repository **before** pointing DNS at GitHub, so nobody else can claim it.

### 1. Create the GitHub repository

Create a new repository on GitHub named **`srath-website`** under **TommyJRath** (https://github.com/new), without a README, .gitignore or license, because this project already has them. It can be public. GitHub Pages on a free account requires a **public** repository. Then push this project:

```bash
git add -A
git commit -m "Initial website"
git remote add origin https://github.com/TommyJRath/srath-website.git
git push -u origin main
```

The first workflow run builds successfully but fails at the deploy step until Pages is enabled. That is expected.

### 2. Enable GitHub Pages with GitHub Actions

Repository → **Settings → Pages → Build and deployment → Source: GitHub Actions**.
Then re-run the workflow (**Actions → Build and deploy to GitHub Pages → Run workflow**).

The site is now at `https://tommyjrath.github.io/srath-website/`. Links and styles will look broken there, because the site is built to live at the root of `srath.dk`. That is fine and resolves after step 3.

### 3. Verify the domain and set the custom domain

1. **Verify `srath.dk` for your account** (prevents domain takeover): your profile picture → **Settings → Pages → Add a domain** → enter `srath.dk`. GitHub shows a TXT record named `_github-pages-challenge-tommyjrath` with a value. Use the name and value exactly as GitHub shows them. Add it at Simply.com (see [DNS](#dns-at-simplycom-without-touching-email)), wait for it to propagate, then click **Verify**. **Keep this TXT record permanently.**
2. **Set the custom domain on the repository**: repository → **Settings → Pages → Custom domain** → `srath.dk` → **Save**.
   When you deploy with GitHub Actions, this setting is what counts. The `CNAME` file in `public/` is ignored by GitHub in that mode and is kept only as documentation and for branch-based publishing.

### 4. Add the DNS records at Simply.com

Add the records from [the DNS section](#dns-at-simplycom-without-touching-email). The DNS check in **Settings → Pages** turns green once the records have propagated (minutes to 24 hours).

### 5. Enable HTTPS

When the DNS check passes, GitHub requests a Let's Encrypt certificate automatically. This can take up to 24 hours. Then tick **Settings → Pages → Enforce HTTPS**.

### 6. Verify `https://srath.dk/app-ads.txt`

Re-run the workflow once the domain is active. The `verify-live` job checks the deployed file. You can also check it by hand:

```bash
npm run verify:live
```

```bash
curl -i https://srath.dk/app-ads.txt
```

You should see `HTTP/2 200`, `content-type: text/plain; charset=utf-8` and the single AdMob line.

### 7. Set the developer website in Google Play Console

For **each app**: Play Console → select the app → **Grow users → Store presence → Store settings → Store listing contact details → Website** → `https://srath.dk` → Save.
AdMob looks for `app-ads.txt` on the domain of this website, so use exactly `https://srath.dk` (no path, no `www`). Menu names in Play Console change from time to time. If you cannot find it, search the Console for "Store settings".

While you are there, update **Policy and programs → App content → Privacy policy** to `https://srath.dk/privacy/<slug>/`.

### 8. Verify in Google AdMob

AdMob → **Apps → View all apps** → the app → **App settings**, or the **app-ads.txt** tab under Apps. Click **Check for updates**. AdMob crawls the developer website from the Play Store listing, so this works only after step 7 is published on Google Play. Crawling can take up to 24 hours or more. If the app is not yet verified, follow the **Verify app** prompt in AdMob, which relies on the same `app-ads.txt`.

## DNS at Simply.com, without touching email

Open simply.com → your account → **srath.dk → DNS**. Edit only the records listed below.

**Records to add or replace** (IP addresses from [GitHub's official documentation](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site#configuring-an-apex-domain)):

| Type | Name | Value |
| --- | --- | --- |
| A | `@` (srath.dk) | `185.199.108.153` |
| A | `@` | `185.199.109.153` |
| A | `@` | `185.199.110.153` |
| A | `@` | `185.199.111.153` |
| AAAA | `@` | `2606:50c0:8000::153` |
| AAAA | `@` | `2606:50c0:8001::153` |
| AAAA | `@` | `2606:50c0:8002::153` |
| AAAA | `@` | `2606:50c0:8003::153` |
| CNAME | `www` | `tommyjrath.github.io` (without the repository name) |
| TXT | `_github-pages-challenge-tommyjrath` | value shown by GitHub in step 3 |

Check the documentation link again when you configure DNS, in case GitHub has changed these addresses.

**Replace, do not add alongside:** if Simply.com already has an `A` or `AAAA` record for `@` or `www` that points to Simply's web hosting, **delete only those web records** and add GitHub's. Leftover web A/AAAA records would send part of your visitors to the old server. If `www` already has an A record, remove it before adding the CNAME, because a name with a CNAME cannot have other records.

With both `srath.dk` and `www` configured, GitHub redirects `www.srath.dk` to `srath.dk` automatically.

**Leave all email records exactly as they are:**

- `MX` records
- `TXT` records containing `v=spf1` (SPF)
- DKIM records (TXT/CNAME, usually `*._domainkey`)
- `_dmarc` TXT record
- Mail-related hosts such as `autoconfig`, `autodiscover`, `mail`, `imap`, `smtp`, `webmail`, and any `SRV` records

Email delivery depends only on these records, not on the `@` A/AAAA records. Before you change anything, check two edge cases:

- **The MX value must not be `srath.dk` itself.** At Simply.com it normally points to Simply's mail servers, which is fine. If it did point to `srath.dk`, mail would follow the A record to GitHub. Contact Simply.com support before changing anything in that case.
- **No mail host may be a CNAME to `srath.dk`.** If, for example, `mail.srath.dk` were a CNAME to `srath.dk`, change it to Simply's mail server hostname, not GitHub's.

**Other advice:**

- Do not create wildcard records (`*.srath.dk`). GitHub warns that they enable domain takeover.
- If you have `CAA` records, make sure one allows `letsencrypt.org`, or HTTPS cannot be issued. If you have no CAA records, nothing is needed.
- Take a screenshot of the DNS zone before you edit it, so you can restore it if needed.

Check from a terminal (Git Bash, WSL or macOS/Linux):

```bash
dig srath.dk +noall +answer -t A
```

```bash
dig srath.dk +noall +answer -t AAAA
```

```bash
dig www.srath.dk +noall +answer
```

```bash
dig srath.dk +noall +answer -t MX
```

The last command should return the same MX records as before your changes. On Windows without `dig`, use `nslookup -type=A srath.dk`.

## Day-to-day updates

1. Edit `content/` (or `public/` for images).
2. Run `npm run check`.
3. Commit and push to `main`. GitHub Actions builds, verifies and deploys within a minute or two. Pull requests are built and verified but not deployed.

GitHub Pages caches pages for about 10 minutes. CSS and JS URLs carry a content hash, so style changes take effect immediately.

## Troubleshooting

| Problem | Fix |
| --- | --- |
| Styles missing on `github.io/<repo>/` | Expected before the custom domain is set. The site is built for the domain root. |
| "Domain does not resolve to the GitHub Pages server" | DNS has not propagated yet, or old Simply A/AAAA records are still present for `@`/`www`. |
| "Enforce HTTPS" is greyed out | Wait for the certificate (up to 24 hours). Check CAA records. |
| `verify-live` fails right after the first deployment with a custom domain | DNS or the certificate is still propagating. Re-run the job later. |
| AdMob says app-ads.txt not found | Check that the Play listing website is exactly `https://srath.dk` and that the change is live on Google Play. Wait 24 hours, then click "Check for updates". |
| Build error about a missing privacy policy | Every app in `apps.json` needs `content/privacy/<slug>.md`. |
